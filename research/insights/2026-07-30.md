## 一句話判斷
法遵與資安這類「強規則導向」的領域已悄悄進入規模化投產，而硬體 EDA 展現出極端集中的痛點，是建立高壁壘 Agent 產品的絕佳標的。

## 二、沒人發現的機會

### 結構性缺口（B1）

1. **`sales-crm` 的 Verify（驗證）任務（Ratio: 0.04）**
   * **推論：真空缺。** 業務端極度依賴資料準確度（如報價單與 CRM 歷史資料的一致性），但目前多數應用集中在生成（寫信），缺乏自動查核。
   * **誰會付錢：** B2B SaaS 業務團隊、Sales Ops。
   * **最小可行做法：** 攔截業務準備送出的報價單或合約草稿，透過 Agent 自動比對 CRM 中的歷史底價與審批規則，標示越權折扣。

2. **`legal-compliance` 的 Orchestrate（編排）任務（Ratio: 0.04）**
   * **推論：合理的不存在。** 法律流程涉及極高風險，律師與法務不可能放任 AI 代理自主編排多步驟決策並直接執行。這不是沒人做，是本來就不該做。**不要碰**。

3. **`design-creative` 的 Configure（配置）任務（Ratio: 0.08）**
   * **推論：真空缺。** 設計師討厭繁瑣的軟體設定，但自動化生成又極度需要嚴格的「品牌視覺規範（Brand Guidelines）」配置來維持一致性。
   * **誰會付錢：** 品牌行銷部門、設計代理商。
   * **最小可行做法：** 建立一個能將企業品牌手冊（PDF）解析為 Agent 可讀取的系統環境變數與提示詞約束條件的配置檔產生器。

4. **`devops-infra` 的 Transform（轉換）任務（Ratio: 0.09）**
   * **推論：真空缺。** DevOps 充滿異質系統，日誌與監控指標格式五花八門。大家都在做佈署（Orchestrate）或監控（Analyze），卻忽略了資料清洗。
   * **誰會付錢：** SRE 團隊、平台工程師。
   * **最小可行做法：** 寫一個輕量級 CLI 技能，讓 Agent 能自動識別任意非標準 Log 格式，並轉換為 ELK/Datadog 可直接吃入的標準 JSON 結構。

### 做一半的領域（B2）

1. **`hardware-eda`（完成率 25% / 樣本 996）**
   * **現況：** 大量工程師嘗試建立 Workflow（748 件），但極少成功上線（243 件）。結合其極低的痛點多樣性（0.07），代表**大家都在卡在同一個難關上**。
   * **卡關原因：** EDA 工具高度封閉、資料格式（如 GDSII、Verilog）特殊、缺乏現代化 API 且受限於地端內網。通用 Agent 框架在此水土不服。

2. **`sales-crm`（完成率 20% / 樣本 130）**
   * **現況：** 需求已驗證，但終端使用者（業務人員）缺乏工程能力將自動化腳本穩定部署為 Production 等級的系統，導致大量半成品。

### 前緣職業（B3）

1. **教會法律師 (n=5, 投產 5)**
   * **痛點：** 天主教法典條文檢索與適用審查繁瑣。
   * **價值：** 這是極度冷門的領域，但投產率 100%。這證明了「越是充滿晦澀規則、需要海量交叉比對的文本工作」，Agent 的破壞力越強。這反映了所有法遵與合規行業的普遍痛點。

2. **資安長 (n=6, 投產 6)**
   * **痛點：** 新創資安風險難量化且難回報董事會。
   * **價值：** C-level 也開始自己寫 Agent Skill。他們要的不是程式碼，而是「高階資料合成與決策量化」。高管級別的資料彙整自動化是巨大的未開發市場。

3. **BIM 工程師 (n=5, 投產 4)**
   * **痛點：** 建築資訊模型跨 Schema 版本易出錯難稽核。
   * **價值：** 這與 IC 設計的 DRC/LVS 檢查邏輯如出一轍。只要涉及龐大的空間/節點模型與嚴格的工業標準，自動化稽核就是剛需。

## 三、短期看法（一個月內）

1. **檢視自己的 Baseband 開發流程：** 盤點你日常工作中類似 BIM/教會法的「純規則稽核」任務（如特定 spec 的邊界條件比對）。這是目前 Agent 最能穩定交付 (Production) 的題材，立刻用 agy 寫成自用 Skill。
2. **避開前端開發與個人生產力的紅海：** 軟體開發 (n=7067) 與個人生產力 (痛點多樣性 0.36，極端碎裂) 的競爭已過度白熱化，不要在此投入心力開發通用工具。

## 四、中期看法（一季內）

1. **押注「Agent-facing」基礎設施：** AI Agent Tooling 領域有高達 60.5% 的 Skill 是給 Agent 用的。未來的軟體架構將從「GUI 給人用」轉向「API/CLI 給 Agent 用」。**推論：** 針對 Agent 設計的輕量級中介軟體（如專門處理 Agent 記憶狀態、權限稽核的套件）會迎來爆發。
2. **硬體 EDA 的破局點在於「橋接器」而非「取代者」：** 既然 EDA 痛點極度集中且難以投產，誰能做出一個安全封裝地端 EDA 工具輸出入格式、讓外部 LLM 能安全呼叫的「膠水層 (Glue layer)」，就能拿下市場。
   * **反證條件：** 如果一季內主流 EDA 大廠（如 Synopsys/Cadence）推出了自帶完整 Agent API 的封閉生態系，這個第三方膠水層的機會就不存在。

## 五、對讀者的具體意涵

1. **你的 Pipeline 護城河很深：** 身為 Baseband 工程師，你所處的硬體領域（Hardware-EDA）痛點多樣性最低 (0.07)，代表只要解決一個核心問題，就能通用於整個團隊。繼續用 Claude Code / ccr 固化你的工作流，這是別人難以複製的 know-how。
2. **Substack 寫作選題：** 放棄寫「如何用 AI 寫程式」。去寫那些在極端環境下成功投產的案例，例如高管與傳產法務的 AI 應用。
3. **非共識題材 HOOK 建議：**
   * `教會律師與IC工程師的共通點：AI落地密碼`
   * `大家都錯了，Agent最大的客戶不是人類`

## 訊號可信度

* **極度可信：** 領域的上線率 (A_traction) 與痛點多樣性 (B4) 具備統計意義。硬體 EDA 的卡關現象與 AI 工具鏈的 Agent-facing 趨勢非常明確。
* **存在偏誤：** 樣本來自 GitHub 公開語料。這會**嚴重低估**硬體設計、金融、醫療等具備嚴格保密協議領域的真實使用量，因為真正的核心 Pipeline 都在內網，不會上傳。
* **樣本不足：** B5 的進場時間分佈僅有一天 (2026-07-26) 的資料，完全無法用於推論時間序列趨勢或市場成長率，本報告已捨棄對此維度的過度解讀。小樣本職業 (B3，n<10) 的數字僅代表存在此現象，不代表發生機率。
