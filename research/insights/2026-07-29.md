# AI 洞察專區 — 2026-07-29

## 一句話判斷
Agent 的 Production 戰場已全面轉向「規範極度明確、容錯率低、以 Verify/Configure 為主的硬核領域」（如法務與資安），而看似熱門的開放式創作與行銷領域則多數停留在玩具原型階段。

## 一、已經拿到成績的領域

在全體平均 Production 上線率為 48.4% 的基準下，真正成功把 AI 部署進正式生產流程的領域呈現高度集中現象：

| 領域 | 樣本數 | 上線率 | 與平均差 | 成功要素 |
| :--- | :--- | :--- | :--- | :--- |
| **legal-compliance** | 418 | 68.4% | +20.0% | 規則高度閉環、合規與合約邊界極度清晰，極適合二元化驗證。 |
| **security** | 2410 | 63.2% | +14.7% | 資安標竿（NIST、CIS）與漏洞特徵皆可機器化解析，斷言明確。 |
| **ai-agent-tooling** | 3274 | 62.6% | +14.1% | 給 Agent 用的比例達 60.5%，開發者自我武裝的工具鏈閉環速度最快。 |
| **devops-infra** | 2071 | 59.4% | +11.0% | 基礎設施 API（K8s、Cloud Provider）標準化程度高，狀態可精確比對。 |

**為什麼成得了？能不能複製？**
- **成功成因**：這些領域的共通點是「輸入與輸出的邊界極度明確」、「存在客觀的 Verifier（驗證器）」。法務有法條比對，資安有漏洞掃描，DevOps 有建置與 CI/CD 狀態。Agent 在這些領域不需要靈感，只需要精確執行與比對。
- **推論：複製可能性**：這個模式能 100% 複製到所有「具有嚴格規格書（Specification）與靜態檢查機制」的領域，例如晶片設計的 Register Map 生成與 Lint 檢查、建築 BIM 模型合規審查。相反地，無法提供客觀二元判定（Pass/Fail）的領域，該成功模式無法複製。

## 二、沒人發現的機會

### 結構性缺口（B1）
以下針對 ratio 最低（與全體任務分佈偏差最大）的任務缺口進行二元判斷：

1. **`legal-compliance` / `orchestrate`（ratio: 0.04, 實際 2 件 vs 期望 48.2 件, n=418）**
   - **判斷**：真空缺（機會）。
   - **理由**：法務領域上線率高達 68.4%，但目前全卡在單一文本的比對與審查，跨系統、多步驟的簽核與風險通報自動流轉（Orchestrate）幾乎為零。
   - **誰會付錢**：企業法務長、跨國合規主管。
   - **最小可行做法（MVP）**：開發跨系統合規簽核 DAG 引擎，將法務審查結果自動轉化為 Jira/Salesforce 的權限變更與通報工作流。

2. **`sales-crm` / `verify`（ratio: 0.04, 實際 1 件 vs 期望 23.9 件, n=130）**
   - **判斷**：合理的不存在（不要碰）。
   - **理由**：銷售業務極度依賴人際互動與非結構化對話，外部環境變動大，不存在固定客觀的機器驗證規則，強行導入 Verify 只會陷入邊際效益遞減。

3. **`security` / `transform`（ratio: 0.08, 實際 11 件 vs 期望 137.8 件, n=2410）**
   - **判斷**：真空缺（機會）。
   - **理由**：資安領域有大量的 Analyze 與 Verify 經驗，但將掃描結果自動「轉換／重構（Transform）」為修正程式碼或修補設定檔的 Agent 工具極度匱乏。
   - **誰會付錢**：DevSecOps 團隊與雲端架構師。
   - **最小可行做法（MVP）**：針對常見資安警告（如 K8s CIS 基準缺失、S3 權限過大），開發單一功能的 CLI 修復轉換工具，輸出自動化的 Pull Request。

4. **`design-creative` / `configure`（ratio: 0.08, 實際 28 件 vs 期望 364.9 件, n=2034）**
   - **判斷**：合理的不存在（不要碰）。
   - **理由**：設計創作本質是主觀視覺呈現，參數渲染與風格調整無法被結構化的組態檔（Configure）嚴格約束。

5. **`data-analytics` / `verify`（ratio: 0.11, 實際 17 件 vs 期望 153.8 件, n=837）**
   - **判斷**：真空缺（機會）。
   - **理由**：數據分析領域目前過度集中於數據提取與圖表生成，但缺乏針對 SQL/DAX 邏輯與跨表對帳的自動化二度驗證機制，導致幻覺數據直接送入高層決策。
   - **誰會付錢**：財務分析師、商業智慧（BI）部門主管。
   - **最小可行做法（MVP）**：在 SQL Pipeline 輸出端掛載對帳機制 Agent CLI，專門進行跨分類帳對齊與數據斷言檢查。

6. **`hardware-eda` / `transform`（ratio: 0.23, 實際 13 件 vs 期望 56.9 件, n=996）**
   - **判斷**：真空缺（機會）。
   - **理由**：硬體 EDA 領域累積了大量工具，但代碼與網表跨語言、跨規格的自動語意轉換（Transform）嚴重缺席。
   - **誰會付錢**：IC 設計房（Design House）與系統廠 CAD 團隊。
   - **最小可行做法（MVP）**：建立針對 Verilog/SystemVerilog 代碼風格轉換與 Register Map 自動轉代碼的語意重構工具。

### 做一半的領域（B2）
下列領域擁有極高的 Workflow 嘗試量，但 Production 完成率極低，代表「需求已驗證，但流程卡在最後一哩路」：

- **`sales-crm`（完成率 0.20，Workflow: 103, Production: 25, n=130）**
  - **卡關原因**：推論：各企業 CRM 資料欄位與業務邏輯高度客製化，缺乏統一 API 標準，導致通用型 Agent 流程無法安定落地的最後一哩路。
- **`education-training`（完成率 0.23，Workflow: 114, Production: 35, n=163）**
  - **卡關原因**：推論：教材與評量生成容易，但個人化適應性學習與教學成效驗證邊界模糊，無法建立開放迴路。
- **`hardware-eda`（完成率 0.25，Workflow: 748, Production: 243, n=996）**
  - **卡關原因**：擁有高達 748 個 Workflow 嘗試，卻只有 243 個成功上線。推論：卡在 EDA 商業工具鏈介面封閉、模擬（Simulation）驗證耗時極長，且 Tape-out 容錯率為零，工程師不敢將 Agent 產出直接送進 Production。

### 前緣職業（B3）
從樣本數極少（n 介於 1-8 件）但 Production 率極高的長尾職業中，挑選具備通用潛力的案例：

- **教會法律師（n=5, Production=5, 樣本數 5 筆）**
  - **痛點**：天主教法典條文檢索與審查架構複雜、教會婚姻法典條文審查缺乏即時引用。
  - **普遍性評估**：痛點極具代表性。這代表「極端利基、歷史累積龐大、先例明確」的法律體系（如專利法、海商法、各國稅法），是尚未被主流工具覆蓋的藍海市場。
- **BIM 工程師（n=5, Production=4, 樣本數 5 筆）**
  - **痛點**：建築資訊模型（BIM）資料品質與合規檢查繁瑣、IFC 程式碼跨 Schema 版本易出錯難稽核。
  - **普遍性評估**：實體工程的跨 Schema 稽核痛點完全普遍。與 IC 設計無異，只要涉及多軟體協作與國際標準規範，即存在強烈稽核軟體需求。
- **生物資訊學家（n=3, Production=3, 樣本數 3 筆）**
  - **痛點**：蛋白質序列驗證與結構預測需跨多平台操作、單細胞分析流程步驟複雜且參數繁瑣。
  - **普遍性評估**：普遍存在於計算生物學。問題不在於單一演算法，而是跨平台 API 串接與多步驟工具鏈的編排（Orchestrate）。
- **C++ 工程師（n=6, Production=5, 樣本數 6 筆）**
  - **痛點**：團隊 namespace 宣告風格不一、命名規範缺乏自動化檢查、記憶體所有權與移動語意複雜易洩漏。
  - **普遍性評估**：底層系統程式開發的共通痛點。強烈需要專屬的靜態代碼與記憶體安全 Agent 稽核器。

## 三、短期看法（一個月內）

1. **強化個人自動化 Pipeline 的「二度驗證（Verify）」機制**
   - **行動**：基於數據（Data Analytics 的 Verify 缺口 ratio 為 0.11），在現有技術 KB 與市場監控 Pipeline 中，加入二元斷言（Assertions）與自動對帳邏輯。在 AI 輸出資料後，強制執行結構與數值合理性檢查，避免無感吸收幻覺資訊。
2. **切入 Hardware-EDA 的「高集中度痛點」CLI 工具開發**
   - **行動**：`hardware-eda` 的痛點多樣性極低（B4 Pain Diversity 僅 0.07，996 個樣本只有 69 種痛點），代表痛點極度收斂。應立即將手邊常用的 Register Map 轉代碼、C/C++ 轉 RTL 腳本打包成符合 Agent 呼叫規範的 CLI 工具，供團隊內部呼叫。
3. **全面避開 Sales-CRM 與 Personal Productivity 的產品開發**
   - **行動**：這兩個領域完成率低（0.20 與 0.26），且 Pain Diversity 高（0.38 與 0.36），需求過於碎片化且無統一邊界，極難打造標準化產品。

## 四、中期看法（一季內）

1. **賭「靜態規範與封閉法規稽核」將全面工具化並吃掉垂直市場**
   - **立場與推論**：推論：未來一季內，法務（Production 68.4%）與資安（63.2%）的成功模式將複製到硬體 EDA 與 BIM 等領域。能夠提供「靜態規範自動檢查」的 Agent 模組將成為 B2B 標配。
   - **證明我錯的訊號**：若三個月後 `hardware-eda` 的 Production 上線率仍卡在 24.4% 甚至下滑，且 Verify 類任務 ratio 未見顯著提升（目前 transform 比率僅 0.23）。
2. **賭 AI Agent 的價值重心在「給 Agent 用的基礎設施」，而非 B2C 應用**
   - **立場與推論**：`ai-agent-tooling` 中「給 Agent 用的比例」高達 60.5%（Production 62.6%），說明目前的真金白銀都在 Agent 彼此呼叫的工具鏈（如 MCP、CLI 工具）。中期內，B2B/DevTool 的變現能力將遠高於面向終端消費者的應用。
   - **證明我錯的訊號**：若 `sales-crm` 或 `writing-content` 的 Production 上線率在下一季突破 50%（目前分別為 19.2% 與 30.3%）。

## 五、對讀者的具體意涵

1. **Pipeline 升級方向**
   - 在現有的電子報、KB 與社群發文流水線中，補齊 `orchestrate`（編排）與 `verify`（驗證）能力。目前 `writing-content` 的 orchestrate 比率僅 0.16，顯示大部分內容流水線卡在單步生成，缺乏多步驟稽核、自動校對與發布流轉。
2. **Substack 非共識選題與 HOOK 標題**
   - **選題一**：破解「AI 降維打擊」迷思 —— 為什麼 Agent 在法律與資安大勝，卻在寫作與行銷慘敗？
     - **HOOK 標題**：`68%上線率真相：別再用AI寫作`（14字）
   - **選題二**：深度剖析 IC 設計 Agent 的困境 —— 996 個 Skill 的集中痛點與 75% 帶不進 Production 的真相。
     - **HOOK 標題**：`IC設計 Agent 為何全卡在半路`（14字）
3. **個人自動化技術路線選擇**
   - 延續使用 CLI 進行厚重工作外包的習慣，但將精力專注於編寫高確定性的「規格與稽核模組（Verifier）」，把生成（Generate）完全外包給 LLM，自己專心做規格與稽核。
