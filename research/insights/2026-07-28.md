# AI 洞察專區 — 2026-07-28

## 一句話判斷
Agent 落地已裂解為兩極：具備明確規範與死板標準的「高壓稽核領域」上線率突破 60%，而仰賴多步驟與開放互動的「業務與硬體設計領域」則高達 75% 滯留在做一半的泥淖中。

## 一、已經拿到成績的領域

| 領域 | 樣本數 | 上線率 | 與平均差 | 成功要素 |
| --- | --- | --- | --- | --- |
| legal-compliance | 418 | 68.4% | +20.0% | 規則極度明確、審查標的定型化，採 Human-in-the-loop 人工最終簽核。 |
| security | 2,410 | 63.2% | +14.7% | 資安防護具備客觀合規標準（如 CIS, SOC2, NIST），Pass/Fail 判定清晰。 |
| ai-agent-tooling | 3,274 | 62.6% | +14.1% | 開發者自我賦能，60.5% 直接面向 Agent 接口，閉環測試與驗證成本低。 |
| finance-investing | 550 | 59.6% | +11.2% | 數據結構化程度高，報表與比率計算具備確定性數學公式。 |

### 為什麼成得了？
- **legal-compliance（法務合規）**：上線率達 68.4%（高出全體平均 20.0%），但 agent_facing_pct 僅 0.2%。
  推論：這代表法務領域並非讓 Agent 全自動運作，而是將 Agent 作為「定型化文本比對與合規檢查」的輔助工具，並由人類律師做最終簽核。這種「明確規範＋人工簽核」的模式是可複製的成功樣板。
- **security（資安）**：上線率 63.2%（+14.7%），樣本數 2,410 件。
  推論：資安成功在於依賴合規清單（如 NIST、CIS 基準）與自動化日誌掃描。判定標準客觀、非黑即白，此成因可複製至任何有明確 SOP 與門檻驗證的工程領域。
- **ai-agent-tooling（AI Agent 工具）**：上線率 62.6%（+14.1%），agent_facing_pct 高達 60.5%。
  推論：工具開發者本身就是使用者，Agent 介面設計直接給 Agent 調用（60.5%），形成了開發、測試到上線的極短閉環。
- **finance-investing（金融投資）**：上線率 59.6%（+11.2%），agent_facing_pct 13.5%。
  推論：成功要素為「算術與財報邏輯的確定性」，避開了非結構化文字生成的幻覺風險。

## 二、沒人發現的機會

### 結構性缺口（B1）

#### 1. `legal-compliance` × `orchestrate`（樣本數 418，觀察值 2，期望值 48.2，Ratio 0.04）
- **判斷**：**合理不存在（不要碰）**
- **理由**：推論：法務合規極度忌諱自動化跨系統串接與自主決策（orchestrate）。法律責任無法歸屬於 Agent，律師與合規官要求每一步都有明確的審查軌跡與人工簽核，絕不可能放手讓 Agent 自主執行跨部門法律動作。

#### 2. `sales-crm` × `verify`（樣本數 130，觀察值 1，期望值 23.9，Ratio 0.04）
- **判斷**：**真空缺（大機會）**
- **理由與痛點**：推論：現有 Sales/CRM 技能過度集中在「自動寫信/生成文案（generate）」，卻嚴重缺乏對 CRM 資料品質、客戶真實意圖與合約條款的「稽核與驗證（verify）」。
- **誰會付錢**：B2B 銷售主管、Sales Operations (SalesOps) 團隊。
- **最小可行做法 (MVP)**：開發 CLI/API 稽核模組，在 CRM 變更 Deal Stage 時，自動比對信件對話紀錄與簽核文件，確保資料真實無缺失才允許推進管道。

#### 3. `security` × `transform`（樣本數 2,410，觀察值 11，期望值 137.8，Ratio 0.08）
- **判斷**：**合理不存在（不要碰）**
- **理由**：推論：資安領域的日誌（Logs）與事件轉換要求嚴格的確定性與不可篡改的證據鏈（Audit Trail）。使用 LLM 進行非結構化 Transform 極易導致資訊遺失或數據失真，業界傾向使用定型化 Parser 而非 AI。

#### 4. `design-creative` × `configure`（樣本數 2,034，觀察值 28，期望值 364.9，Ratio 0.08）
- **判斷**：**真空缺（大機會）**
- **理由與痛點**：推論：設計領域充斥著圖像生成（generate），但極缺將品牌規範（Design System）、顏色代碼與版型參數進行「配置與設定（configure）」的工具。設計師與前端常常耗費時間手動對齊 Token。
- **誰會付錢**：企業前端開發團隊、UI/UX 設計主管。
- **最小可行做法 (MVP)**：讀取 Figma Token 或品牌規範 JSON，自動轉換並配置為前端專案（CSS Variables / Tailwind）約束層的 CLI 模組。

#### 5. `devops-infra` × `transform`（樣本數 2,071，觀察值 11，期望值 118.4，Ratio 0.09）
- **判斷**：**真空缺（大機會）**
- **理由與痛點**：推論：DevOps 領域大量依賴 IaC（Terraform, K8s yaml），但跨平台/跨架構的語法轉換（如 Docker-compose 轉 Helm/K8s、CloudFormation 轉 Terraform）極少有人用 Agent 做妥善處理。
- **誰會付錢**：SRE 團隊、雲端架構師。
- **最小可行做法 (MVP)**：結合 AST 靜態語法解析與 LLM 的二階段 IaC 轉換技能，專門輸出具備語法與合規檢查的 Terraform / K8s 設定檔。

### 做一半的領域（B2）

#### 1. `sales-crm`（完成率 0.20 ｜ 103 個 Workflow vs 25 個 Production）
- **卡在哪一關**：推論：卡在外部系統（Salesforce / HubSpot）API 授權存取與商業對話非結構化帶來的「結果驗證困難」。大家寫了大量自動化流程，但因為不敢承擔發錯信或搞砸客戶關係的風險，無法推上 Production。

#### 2. `education-training`（完成率 0.23 ｜ 114 個 Workflow vs 35 個 Production）
- **卡在哪一關**：推論：卡在「教學評量與問答的幻覺控制」。自動化作業批改或適應性教學 Workflow 容易產生不穩定的評分結果，缺乏個性化反饋的驗證閉環。

#### 3. `hardware-eda`（完成率 0.25 ｜ 748 個 Workflow vs 243 個 Production）
- **卡在哪一關**：推論：卡在封閉的商業 EDA 工具 API（Synopsys / Cadence）、腳本語法精準度要求極高，以及缺乏自動化的 Formality / DRC 驗證反饋機制。雖然工程師嘗試了 748 個 Workflow，但高達 75% 因無法通過確定性檢驗而無法成為正式 Production 工具。

### 前緣職業（B3）

#### 1. `BIM工程師`（n=5, production=4, max_stars=254）
- **痛點**：建築資訊模型 (BIM) 資料品質與合規檢查繁瑣、IFC 程式碼跨 Schema 版本易出錯難稽核。
- **是否為普遍痛點**：推論：是的。營建業數位轉型中，BIM 模型跨軟體與法規的自動化檢核是全球性的硬需求，屬尚未被滿足的高價值合規市場。

#### 2. `教會法律師`（n=5, production=5, max_stars=1381）
- **痛點**：天主教法典條文檢索與審查架構複雜、教會婚姻法典條文審查缺乏即時引用。
- **是否為普遍痛點**：推論：代表了「封閉高階專業文獻」的檢索痛點。類似需求普遍存在於專利法、海商法等特殊法律領域，是明確的專業 RAG 需求。

#### 3. `ServiceNow 開發者`（n=3, production=3, max_stars=51）

- **是否為普遍痛點**：推論：是的。企業級 PaaS 平台（ServiceNow, SAP, Salesforce）開發者普遍面臨封閉語法、文檔稀缺與作用域陷阱，這是極具付費能力的 Enterprise 痛點。

#### 4. `生物資訊學家`（n=3, production=3, max_stars=159）
- **痛點**：蛋白質序列驗證與結構預測需跨多平台操作、單細胞轉錄組分析流程複雜且參數繁瑣。
- **是否為普遍痛點**：推論：是的。生醫研發極度需要跨 CLI 工具與數據格式的自動化串接（Orchestration）。

## 三、短期看法（一個月內）

1. **重構個人 CLI Pipeline：從「生成 (Generate)」全面改為「稽核 (Verify)」**：
   推論：數據顯示 Verify 在數據分析（ratio 0.11）、運維（ratio 0.14）、發文內容（ratio 0.17）均呈現嚴重結構性缺口。應立即在個人的電子報發文與知識庫 Pipeline 中，加入自動化 Format 檢測與 Fact-checking 的門檻模組。
2. **開發晶片設計 / EDA 腳本的「語法與規則稽核工具 (Verify/Configure)」**：
   推論：`hardware-eda` 累積了 748 個 Workflow 但上線率僅 24.4%，代表需求極大卻缺乏最後一哩路。利用 agy / ccr 建立專門針對 TCL/Verilog 腳本規範的 static-analysis skill，能立刻提高自動化腳本的可用性。

## 四、中期看法（一季內）

1. **賭「專業領域 Agent 稽核層（Audit Layer）」將大於「通用 Agent 工具」**：
   - **賭的立場**：未來一季，市場資源會從「開發通用 Agent 框架」轉向「針對特定領域寫死 Verify / Check 模組」。
   - **反證 / 證明我錯的訊號**：若 `ai-agent-tooling` 的 production_pct（目前 62.6%）繼續上升突破 75%，且其他專業領域的 completion_ratio（如 EDA 目前 0.25）未見提升，代表通用 Agent 依然吸乾所有資源，專業稽核層需求尚未爆發。
2. **賭「硬體 EDA 自動化將出現專屬 Middle-layer 介面」**：
   - **賭的立場**：`hardware-eda` 75% 做一半的原因是缺乏連接 EDA API 的標準化抽象層，一季內開源社群將出現專門對接 EDA 邏輯的適配器。
   - **反證 / 證明我錯的訊號**：若 `hardware-eda` 的總樣本數（目前 n=996）在下一季顯著下滑，或 production_pct 降至 20% 以下，代表工程師放棄用 LLM 做 EDA 自動化，退回傳統手寫腳本。

## 五、對讀者的具體意涵

1. **個人 Pipeline 避坑指南**：
   推論：你的 Substack 發文與市場監控 Pipeline，切忌嘗試全自動「無人值守串接（Orchestrate）」（寫作領域 orchestrate ratio 僅 0.16）。建議採取「自動檢索 (Retrieve) ➔ 自動稽核 (Verify) ➔ 人工最終微調 (Human Review)」的架構，才能避免 Pipeline 經常中斷。
2. **Substack 非共識寫作題材**：
   - **題材一**：揭露硬體工程師在 AI 浪潮下的真實困境 —— 解析為何 IC 設計有 748 個 Workflow 卻有 75% 卡在驗證（completion_ratio 0.25）。
   - **題材二**：打破大模型生成幻覺 —— 用法務與資安高達 60%+ 的上線率證明「嚴格稽核（Verify）」才是 AI 自動化落地的唯一密碼。
   - **HOOK 標題 1（≤15 字）**：晶片設計 AI 化：75% 卡在驗證
   - **HOOK 標題 2（≤15 字）**：AI落地真相：生成玩票，稽核收錢

## 訊號可信度

- **結論極為堅固部分**：
  - 全體樣本數高達 24,944 件（global_production_pct = 48.4%），總體基線具備極高統計信度。
  - 軟體開發（n=7067）、AI Agent 工具（n=3274）、資安（n=2410）、DevOps（n=2071）、設計（n=2034）樣本數均大於 2,000 件，其上線率與任務缺口比率結果非常穩定。
- **初步跡象 / 受限部分**：
  - **系統性偏差**：樣本僅來自 GitHub 公開數據，會**系統性低估**法務（n=418）、金融（n=550）、醫療（n=564）特別是 IC 設計/EDA（n=996）在企業內部閉源環境的真實自動化普及率。
  - **長尾職業樣本極小**：`B3_niche_professions` 的長尾職業樣本數極小（n=3~8），雖然上線率高，但個案屬性重，不可直接外推為行業普遍現象。
  - **時間序列資料不足**：`B5_by_first_seen` 目前僅有單日（2026-07-26）資料，不足以判斷時間動態趨勢。
  - **LLM 分類穩定度**：小樣本領域（如 sales-crm n=130、education-training n=163）的分類比率受單一樣本影響較大，引用時須注意樣本數限制。
