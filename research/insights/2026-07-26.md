# AI 洞察專區 — 2026-07-26

## 一句話判斷
AI Agent 的落地戰場已經全面從「文字/程式碼生成（Generate）」轉移至「確定性驗證與系統調度（Verify/Orchestrate）」，凡是不具備自動稽核機制的工具都陷入 completion ratio 不足 30% 的滯銷卡關狀態。

---

## 一、已經拿到成績的領域

在全體平均上線率（production_pct）為 42.3% 的基準下，高上線率領域展現出強烈的共通特徵：強介面規範、低容錯空間、以及可自動化驗證結果。

| 領域 | 樣本數 | 上線率 | 與平均差 | 成功要素 |
| :--- | :--- | :--- | :--- | :--- |
| **security** | 265 | 64.9% | +22.6% | 推論：具備明確的標準化規範（如 CVE、NIST）與確定性 CLI 掃描工具，比對結果客觀且容錯率低，極易納入自動化 CI/CD pipeline。 |
| **legal-compliance** | 88 | 63.6% | +21.3% | 推論：主要應用於結構化條文檢索與專利/合規對照比對，而非讓 AI 自由發揮生成，任務範疇聚焦且驗證邊界清晰。（註：樣本數 n=88，受限於 GitHub 公開 repo 偏誤） |
| **devops-infra** | 337 | 62.6% | +20.3% | 推論：擁有極度成熟的 API 與 CLI 介面（如 Docker, K8s, Terraform），執行結果可由 Exit Code 或系統狀態直接自動化驗證。 |
| **ai-agent-tooling** | 844 | 45.3% | +3.0% | 推論：agent_facing_pct 高達 59.2%，顯示該領域已全面轉型為「給 Agent 呼叫的標準介面與基礎建設」，而非單純給人類使用的面板。 |

推論：這些領域成得了的關鍵在於**「結果可被程式碼自動檢查（Deterministic Verifiability）」**。這個成因可以完全複製到 IC 設計（EDA 工具呼叫與 LVS/DRC 檢查）以及韌體自動化測試中。

## 二、沒人發現的機會

### 結構性缺口（B1）

全體任務分佈基準為：`configure` (17.1%)、`orchestrate` (15.6%)、`verify` (15.0%)、`analyze` (12.5%)、`retrieve` (9.9%)、`transform` (8.0%)、`generate` (21.9%)。以下為 ratio 最低（<0.30）的結構性缺口分析：

1. **`healthcare-bio` × `generate`（ratio: 0.04，觀察 1 vs 期望 25.4）**
   - **判斷：合理不存在（不要碰）**
   - **原因**：推論：醫療生技極度忌諱 AI 幻覺生成內容，醫療事故責任與法規監管極為嚴苛，此領域的真空是業界刻意避險的結果，盲目投入文字生成型 AI 工具無異於自殺。

2. **`personal-productivity` × `verify`（ratio: 0.07，觀察 3 vs 期望 45.5）**
   - **判斷：真空缺（巨大機會）**
   - **誰會付錢**：高薪專業人士、自由職業者、管理者。
   - **最小可行做法**：開發 CLI 工具，自動抓取每日 Git log、對話紀錄與 Calendar/Jira，自動比對並稽核「承諾事項與實際交付的落差（Execution Auditor）」。
   - **原因**：推論：市面上全是幫人生成草稿的生產力工具，卻完全沒有幫人「稽核進度與檢視承諾」的嚴格驗證工具。

3. **`sales-crm` × `verify`（ratio: 0.13，觀察 1 vs 期望 7.5）**
   - **判斷：真空缺（高價值機會）**
   - **誰會付錢**：B2B 銷售主管、資深合規經理。
   - **最小可行做法**：對接 CRM 與 Email/Zoom 逐字稿，自動驗證業務員是否對客戶做出超出公司合規上限的承諾或價格折讓。
   - **原因**：推論：銷售領域大量使用生成型 AI 寫開發信，但對銷售品質與合規的自動化稽核幾乎為零。

4. **`finance-investing` × `transform`（ratio: 0.14，觀察 2 vs 期望 14.5）**
   - **判斷：真空缺（高價值機會）**
   - **誰會付錢**：量化交易員、財務分析師、投資機構研究員。
   - **最小可行做法**：專門解析複雜 PDF 財報/財測總帳表格，並強制轉換為 Python Dataframe / JSON 的型態安全轉換引擎。
   - **原因**：推論：金融領域不缺資料檢索（retrieve），缺的是把各類非結構化財報精確轉換為結構化 API 資料流的中繼站。

5. **`security` × `orchestrate`（ratio: 0.15，觀察 6 vs 期望 41.2）**
   - **判斷：真空缺（技術壁壘機會）**
   - **誰會付錢**：中大型企業 SecOps 團隊。
   - **最小可行做法**：基於 CLI / Playbook 的多資安工具跨平台調度 Agent（自動串接掃描、封鎖 IP、通報 Slack）。
   - **原因**：推論：資安單點工具很多，但跨工具的自動化回應流程調度（SOAR）上線率極低，市場缺乏輕量級的 Agent 調度器。

6. **`legal-compliance` × `orchestrate`（ratio: 0.15，觀察 2 vs 期望 13.7）**
   - **判斷：合理不存在（不要碰）**
   - **原因**：推論：法規合規與合約簽署涉及終極法律責任，業界流程要求「Human-in-the-loop」，無法接受由 Agent 進行全自動的多階段閉環調度（Orchestrate）。

### 做一半的領域（B2）

此區塊代表「需求已經過驗證（workflow 數量高），但技術或產品化出現瓶頸（production 完成率低）」：

1. **`education-training`（完成率 0.19，n=78，workflow 54, production 13）**
   - **卡關原因**：推論：教材生成（generate）極容易，但缺乏針對學生反饋的自動化批改與動態教學進度驗證機制（verify 僅有 2 件），導致無法封閉形成商業產品。

2. **`personal-productivity`（完成率 0.24，n=303，workflow 210, production 65）**
   - **卡關原因**：推論：個人工作流程極度分散且個人化，現有工具大多只做半套（寫稿、摘要），缺少自動化觸發機制與邊界檢查（verify 僅 3 件），使用者試用後即放棄。

3. **`research-academia`（完成率 0.29，n=186，workflow 124, production 51）**
   - **卡關原因**：推論：學術論文搜尋與文獻整理（retrieve）容易，但論文間數據的交叉轉換（transform）與實驗邏輯的自動嚴謹度檢查無法落實，導致研究員只能停留在手動驗證階段。

### 前緣職業（B3）

從長尾領域中挑選已將 AI 落地於極度專業場景的前緣職業：

1. **逆向工程師（n=7, production=6, max_stars=930）**
   - **痛點**：閉源執行檔黑箱逆向、未公開通訊協定封包格式與狀態機逆向。
   - **普遍性判斷**：推論：這是資安與韌體工程的普遍痛點。將二進制檔案與網路封包結構丟給 AI 搭配 Ghidra/Wireshark CLI 進行自動化協定推導，是高價值的剛性需求。

2. **網路工程師（n=7, production=5, max_stars=6780）**
   - **痛點**：傳統網路連線排查工具輸出格式難解析、EVE-NG 網路拓撲建置缺乏自動化 QA。
   - **普遍性判斷**：推論：網路運維資料格式極度雜亂，且拓撲部署前缺少自動化門檻檢查。這對所有大型資料中心與企業網管都是通用痛點。

3. **C++ 工程師（n=6, production=5, max_stars=3495）**
   - **痛點**：C++ 記憶體所有權與移動語意複雜易洩漏、namespace 與命名規範缺乏自動化檢查。
   - **普遍性判斷**：推論：通用 Coding AI（如 Copilot）對 C++ 記憶體安全與邊界檢查支援度極差。系統級工程師強烈需要結合靜態分析與 Agent 的深度稽核工具。

4. **BIM 工程師（n=5, production=4, max_stars=254）**
   - **痛點**：建築資訊模型（BIM）資料品質與合規檢查繁瑣、IFC 程式碼跨 Schema 版本易出錯。
   - **普遍性判斷**：推論：傳統建築工程轉型數位化過程中，Schema 格式稽核與合規檢查是極度費時的痛點，證明了「傳統產業垂直 Schema 驗證」具有極高工具化潛力。

## 三、短期看法（一個月內）

1. **全面停做「純生成型（Generate-only）」Pipeline，全面導入「稽核（Verify）」關卡**
   - 立即在現有的 Substack 與知識庫自動化流程中，加入 Markdown 格式檢查、引用連結有效性驗證與邏輯邊界稽核的 CLI 工具。

2. **開發基於 CLI 的強型態「資料轉換器（Transform Skill）」**
   - 針對 BTC 監控與 WiFi 知識庫，寫死 Schema 輸入輸出介面，不讓 LLM 自由發揮 JSON 格式，解決 Agent 對外呼叫時的解析崩潰問題。

## 四、中期看法（一季內）

1. **賭注一：Agent-Facing 介面的工具將徹底碾壓 Human-Facing 面板工具**
   - **立場**：未來一季，專門給 Claude Code / agy / ccr 等 CLI Agent 呼叫的 Skill/Tool 數量與使用率將出現爆發性成長。
   - **證偽訊號**：若 `ai-agent-tooling` 的 `agent_facing_pct`（目前 59.2%）在一季內下滑至 40% 以下，代表開發者重新回歸傳統 UI 互動模式，則此賭注失敗。

2. **賭注二：「驗證型（Verify）」垂直工具箱將迎來第一波商業變現**
   - **立場**：個人生產力與教育領域的完成率（completion ratio）將從目前的 0.24 與 0.19 翻倍，關鍵在於會出現專門做「進度稽核/邏輯邊界檢查」的閉環工具。
   - **證偽訊號**：若一季後 `personal-productivity` 的 B1 `verify` ratio（目前 0.07）依然低於 0.15，代表市場依然無法克服個體工作流碎片化的驗證難題。

## 五、對信哥的具體意涵

1. **Pipeline 升級方向**：
   - 信哥現有的自動化 Pipeline（Substack、BTC 監控、知識庫）應立即補強 **Verify** 模組。重度外包給 CLI Agent（agy/ccr）時，信哥只需撰寫「稽核規格（Spec Auditor）」，讓 Agent 自己跑對照檢查，徹底釋放手動審核精力。

2. **Substack 寫作與選題建議（非共識切入點）**：
   - 業界目前陷入「一直用 AI 生成垃圾內容」的泥淖，信哥可發揮 Baseband IC / 韌體工程師的嚴謹視角，撰寫非共識硬核文章：
     - **HOOK 標題 1**：`AI寫程式沒人在驗證？個人生產力的致命缺口`
     - **HOOK 標題 2**：`別再用AI做生成！資安與韌體稽核才是硬道理`
     - **HOOK 標題 3**：`逆向與EDA前緣：極客工程師如何把Agent當CLI寫`

3. **技術與工具佈局**：
   - 針對 Baseband / IC 設計領域，聚焦於「C++ 記憶體安全稽核」與「EDA 工具 CLI 腳本調度（Orchestration）」的 Skill 封裝，這是在公開 GitHub 幾乎看不到（n=36）但私有領域極度稀缺的競爭壁壘。

## 訊號可信度

- **高可信度（資料充足且硬性）**：
  - 全體任務分佈（n=5397）與三大上線率領域 `software-dev` (n=1809)、`ai-agent-tooling` (n=844)、`devops-infra` (n=337)、`security` (n=265)。
  - `ai-agent-tooling` 領域中 `agent_facing_pct` 高達 59.2% 的趨勢極為明確。

- **中等可信度（具備結構性證據，但需留意樣本偏誤）**：
  - B1 結構性缺口與 B2 完成率數字。
  - **重要警語**：資料源僅來自 GitHub 公開 Skill Repo，會**系統性低估**法務（legal-compliance n=88）、醫療（healthcare-bio n=116）、金融（finance-investing n=182）以及 IC 設計（hardware-eda n=36）的真實企業內部落地狀況。

- **初步跡象 / 低可信度（僅供前緣觀察）**：
  - B3 前緣職業（如逆向工程師 n=7、教會法律師 n=5）。此類數據樣本極小（n<10），比例容易受單一項目極端值影響，僅代表「極少數極客已驗證成功」的前緣訊號，不可直接推論為大規模統計數據。
  - Repo 的 Stars 數僅代表該 GitHub 專案總體知名度，不可作為特定 Skill 本身受歡迎度的直接證據。
  - 時間分佈（B5）僅有 2026-07-26 單日觀察值，無法提供跨時間的動態趨勢判斷。
