# 資料策略：24 萬筆語料要怎麼處理才會有洞察

GitHub 上有 **246,584 個公開 SKILL.md**。這份文件說明我們實際能拿到多少、為什麼不需要全拿、
以及在這個量級上要怎麼分析才會得到洞察而不是一堆統計數字。

## 一、覆蓋率的真正瓶頸

不是 API 額度，是**每個查詢最多只能取回 1000 筆**（10 頁 × 100），與 `total_count` 顯示幾萬筆無關。

所以要提高覆蓋率，唯一的辦法是切出夠多的**不重疊分區**。做法是對檔案大小做遞迴二分
（`bin/harvest_full.py`）：查一個區間，若回報總數 > 900 且區間還能再切就對半切、各自遞迴，
否則就翻頁抓乾淨。分區密度會自動貼合實際分佈——檔案多的大小區間切得細，稀疏的區間不浪費查詢。

實務上的成本：code search 限 30 次/分鐘，每個分區要 1 次計數 + 最多 10 次翻頁。
要完整覆蓋 24 萬筆需要 250 個以上的滿載分區，實際因分佈不均需要上千個，
換算約 10 小時以上的純查詢時間，外加 24 萬次內容抓取。所以這是**持續累積**的工程，不是一次跑完的事。

## 二、為什麼「全部拿到」不是重點

比例估計的精度只跟樣本數的平方根有關。以佔比 33% 的軟體開發為例（95% 信賴區間）：

| 樣本數 | 誤差範圍 |
|---:|---|
| 5,397 | ±1.25pp |
| 50,000 | ±0.41pp |
| 246,584 | ±0.19pp |

**把樣本從 5 千拉到 24 萬，主要比例的估計只從 ±1.25pp 進步到 ±0.19pp** ——
對「軟體開發佔三分之一」這種結論完全沒有影響。

真正會因為樣本變大而改變的是**長尾**：

| | n=5,397 | n=50,000 |
|---|---|---|
| 硬體/EDA（真實佔比約 0.7%） | 預期 38 件，實際 36 件 | 預期約 350 件 |
| 能否分析其內部結構 | 不行，樣本太小 | 可以 |
| 前緣職業（佔比 < 0.1%） | 幾乎抓不到 | 開始成形 |

**結論：擴大樣本的價值在長尾與稀有類別，不在主要比例。**
因此擴充策略優先服務「稀有領域的內部結構」與「還沒被命名的新類別」，而不是把頭部數字再算精確一點。

## 三、分類要怎麼擴展：LLM 當標註員，本機模型當放大器

用 LLM 逐筆分類 24 萬筆不可行（5,400 筆就跑了一小時）。但 LLM 已經標好的那幾千筆是很好的訓練資料。

```
LLM 標種子（數千筆） → 本機 TF-IDF + Logistic Regression 學會模式 → 標全量 → LLM 只負責解讀
```

`bin/train_classifier.py` 會對每個欄位輸出 5-fold 交叉驗證準確率，並與
「全部猜最常見類別」的多數類基準對照——**贏不過基準的欄位不該拿來下結論**。

模型標的資料會帶 `label_source: model` 與各欄位信心值，與 LLM 標的分開存。
分析時可依信心門檻篩選。

### 這個做法的限制（必須誠實面對）
- 模型只學得到 LLM 標註裡的模式，**LLM 的偏誤會被完整複製並放大**。
- 種子樣本沒出現過的新類別，模型永遠標不出來——這是下一節要解決的。
- 信心值是模型的自我評估，不是正確率保證。

## 四、怎麼發現「我沒想到的類別」

上面的分類器有個根本限制：它只能把東西塞進我預設的 18 個領域。
真正的新東西——某個還沒有名字的用法——會被硬塞進 `other` 或最像的類別，然後消失。

所以需要一條**無監督**的路線（`bin/cluster.py`）：
1. 對全量語料做 TF-IDF 向量化
2. KMeans 分群（k 遠大於 18，例如 120–200）
3. 每群抽出最具代表性的詞與最靠近中心的樣本
4. **只把這 120–200 個群的代表樣本餵給 LLM 命名**——這是唯一的 LLM 成本

若某個群的成員在既有分類裡散落在多個領域、或大量落在 `other`，
那就是一個**現有分類法沒有涵蓋的新用法**，也就是最有價值的發現。

## 四之二、分層過取樣：怎麼把長尾撈起來又不弄髒母體

既然擴大樣本的價值在長尾，最有效率的做法就不是無差別地擴充，而是**針對稀有層過取樣**。
`bin/harvest_eda.py` 用 48 個 EDA/IC 詞彙（分成 chip-design / verification / adjacent-hw 三層）
去撈硬體相關的 SKILL.md，撈到的密度遠高於母體真實比例。

**這會製造一個陷阱**：如果把這些樣本直接混進總表，「硬體/EDA 佔 0.67%」就會被自己污染成假的。

所以每一筆過取樣樣本都標記 `sample: "targeted-<topic>"`（例如 `targeted-eda`、
`targeted-wifi`），並且：

| 用途 | 使用哪些樣本 |
|---|---|
| 估計整體比例、領域分佈、缺口訊號 | **只用中立樣本**（`bin/opportunity.py` 明確排除） |
| 分析 EDA 內部結構：誰在做、什麼層級、卡在哪 | 中立 + 過取樣全用 |
| 頁面上的「硬體/EDA 佔比」 | 只用中立樣本計算 |

這是分層抽樣的標準做法：稀有層過取樣以取得足夠的層內統計力，同時保留原始權重資訊。
每筆樣本另存 `eda_tier`（來自哪一層詞彙）與 `matched_terms`（被哪些詞撈到），
讓之後能分辨「真正的晶片設計」與「只是提到 FPGA 的嵌入式專案」。

## 五、洞察是怎麼被找出來的

有了大量分類資料之後，洞察不是靠「看統計表」得來的，而是靠幾個明確定義的訊號
（全部在 `bin/opportunity.py` 裡以純計算實作）：

| 訊號 | 定義 | 回答什麼問題 |
|---|---|---|
| 結構性缺口 | 該領域某任務型態的「實際 / 期望」比值 | 誰缺了什麼能力 |
| 完成率 | production / (workflow + production) | 哪裡是做一半沒做完 |
| 動能 | 近半期佔比 − 前半期佔比 | 需求在長還是在退 |
| 痛點多樣性 | 不重複痛點數 / 樣本數 | 需求是否還沒被統一方案收斂 |
| 前緣職業 | 樣本 1–8 件但已有 production | 誰最早把 AI 帶進自己的專業 |

**兩個訊號同時成立時最值得看**：例如「需求在長（動能為正）」+「能力缺席（缺口比值低）」
= 需求正在擴大但沒人補上這塊能力。

最後一步才交給 LLM：把訊號表解讀成人話，並**逐一判斷缺口是真空缺還是合理的不存在**
（醫療生技幾乎沒有生成類 skill，是該行業刻意避開 AI 幻覺責任，不是機會）。
判錯方向比不寫更糟，這是 LLM 在這條管線裡唯一無法被腳本取代的工作。

## 六、成本結構

| 步驟 | 誰做 | 邊際成本 |
|---|---|---|
| 分區搜尋、內容抓取 | 腳本 | 0 token，受 API 速率限制 |
| 特徵化、分群、訓練、推論 | 本機 scikit-learn | 0 token |
| 統計、交叉表、機會訊號 | 腳本 | 0 token |
| 種子標註 | LLM | 一次性，數千筆 |
| 群集命名 | LLM | 120–200 次，僅在重新分群時 |
| 訊號解讀 | LLM | 每日一次，輸入只有幾 KB 訊號表 |

**新增一筆 skill 的邊際 token 成本是零。**

## 七、累積 vs 重生成：來自 Karpathy LLM Wiki 的修正

[Karpathy 的 LLM Wiki 概念](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
點出 RAG 的根本問題：每次查詢都從頭發現知識，「LLM 是個才華橫溢但查完就失憶的研究者」，
沒有累積、沒有合成。他的解法是三層（raw sources / wiki / schema）＋三操作（ingest / query / lint）。

**這正好是本專案原本的缺陷。** 每日洞察是「重新生成」而非「累積修正」——
昨天講錯的話今天不會被發現，只會多一個 dated 檔案。實例：本專案曾對「硬體領域的 verify 佔比」
先後宣稱 8.3% → 2.24x → 16.0%，前兩者分別是樣本不足（3/36）與模型過度自信造成的錯誤。

已採納的部分：`bin/wiki_lint.py` 實作 lint 操作，把歷來報告中的量化宣稱按指標跨檔比對，
相對差異超過 25% 即標記，強迫「要嘛修正舊報告、要嘛說明為什麼數字變了」。

實作時踩到的兩個坑（都會讓 lint 失去意義）：
1. **限定詞窗口太寬會誤配**：`healthcare-bio（53.4%）…遠高於總體平均（42.3%）`
   會把「總體平均」錯套到 53.4 上。
2. **窗口太窄會漏抓**：`全體任務分佈基準為：verify (15.0%)…` 的限定詞在句首。

解法是以**句子**為單位判定：限定詞必須與數字同句且在其之前。
並且加了自我測試——故意塞入矛盾值確認 lint 會觸發，
因為**一個永遠不觸發的 lint 比沒有 lint 更危險**，它會給假的安全感。

已實作、待 fresh master 首次 production ingest：wiki 實體頁面（每個領域一頁、保留 owner notes、
隨時間追加 evidence history；同日修正必須留下 revision note）。目前公開 Release 與最新
`model_report.json` 的種子數不一致，freshness gate 會阻止用 stale snapshot 重建。
