## 🔴 官方變動（事實）

- **Claude Code v2.1.219 & v2.1.220 發布**：
  - **預設模型切換**：`claude-opus-5` 成預設 Opus 模型，提供 1M Context 視窗與 Fast mode（$10/$50 per Mtok）。這代表架構支援更長對話軌跡，但需注意 Context 膨脹帶來的注意力稀釋與 Token 成本暴增。
  - **沙盒網路防禦（`sandbox.network.strictAllowlist`）**：新增嚴格白名單設定，阻擋未授權主機連線且不再主動提示。這能直接解決自動化 CLI 執行腳本時遭外部網路連線偷渡資料的漏洞。
  - **工作流優化與 Hook 擴充**：`/code-review` 轉為背景子 Agent 執行，不再佔用主視窗對話；新增 `DirectoryAdded` hook，方便在 Session 途中動態擴充工作目錄。
- **`anthropics/claude-plugins-official` 例行 Bump**：
  - 官方密集自動更新外掛依賴（如 `remember`, `hyperframes`, `auth0`, `pydantic-ai`, `databricks` 等），無新增或廢棄外掛。
- **`anthropics/skills` 無異動**：
  - 官方 Skill 目錄維持 17 個，無提交變動。

## 🌊 社群風向（訊號，非事實）

1. **1M Context 時代下的「Context 稀釋」與注意力衰減問題成焦點**
   HN 熱討與 arXiv 最新論文（*How Agent Skills Fail under Long Contexts*）共同指出：即使模型 Context 擴張至 1M，隨著 Tool 呼叫軌跡增長，Agent 對 Skill 規範與約束的遵從度會大幅下降。這代表單純把所有規範塞進 Context 是無效的，必須採用「動態漸進揭露」與強硬門禁（Intake Gate）。
2. **多 Agent 組合攻擊（Kill Chain）與通道漏洞受安全圈高度關注**
   arXiv 發布 *ChannelGuard* 與 *ChainWatch*，證明即使單一 Agent 或單次 MCP 工具呼叫通過安全審查，攻擊者仍可在多 Agent 之間的未監控通道（unmonitored channel）注入指令，或將多個看似合法的工具呼叫組合為惡意攻擊鏈。
3. **Karpathy 研發踩坑經驗被工程化為防護規約**
   社群 repo `0xwilliamortiz/andrej-karpathy-skills` 與 `finna/Finn-loop` 暴增，反映開發者不再相信 Agent 的自主發揮，轉而將「限制 Agent 亂改已運作程式碼」的踩坑經驗寫成硬性 Checkpoint（Spec ➔ Build ➔ Review 嚴格三階段分開）。
4. **跨 Harness 的離線 Session 上下文轉移需求興起**
   出現如 `resume-skills` 與 `handoff-skill` 等專案，嘗試將對話 Context 格式化為通用中立結構，解決在 Claude Code / Codex / Antigravity / Cursor 之間切換時丟失狀態的痛點。

## 🎯 策略建議

### 短期（一週內）
1. **啟用 Claude Code 嚴格網路白名單**：
   在 CLI 設定中加入 `sandbox.network.strictAllowlist`，僅允許 pipeline 必要的網域（如 Substack API、Cloudflare、指定數據源），全面阻擋非授權外連。
2. **檢視並吸收 Karpathy 防護規約**：
   不用直接安裝第三方 Skill，手動人肉審閱 `0xwilliamortiz/andrej-karpathy-skills` 中的 Markdown 內容，將其中防範「Agent 擅自重構運作中程式碼」的規則，抽離並寫入現有 pipeline 的 `.claude/rules` 或 agy 系統提示詞中。
   - **驗證步驟**：使用 `git clone` 下載至 `<appDataDir>/scratch/` 獨立目錄 ➔ 純文字人肉檢查是否有隱藏指令 ➔ 手動複製純規約內文。

### 中期（一個月內）
1. **重構 Pipeline 之 Context 載入策略**：
   針對 Substack 發文與知識庫自動化流程，實施分段加載（Progressive Disclosure）。不要將長文與厚重 context 一次灌入 Opus 5，應改由主控 Agent 依需求動態 view 局部檔案，防止因 Context 過長導致 Skill 規範失效與 Token 浪費。
2. **針對關鍵 Write 權限 Tool 加上二階段確認**：
   回應 *ChainWatch* 提到的 MCP 攻擊鏈風險，凡涉及修改知識庫檔庫、發布 Substack 或變更系統組態的動作，Agent 必須輸出中繼計畫並經過人體稽核或獨立 Verifier 檢查後才可執行。

### 長期（一季內）
1. **實施「特權分離與隔離沙盒」自動化架構**：
   根據最新安全趨勢，單一高特權 Agent 極易受穿透攻擊。讀者的自動化體系應全面走「雙 Agent 隔離」路線：前段由 Planning Agent 在低權限沙盒處理未過濾輸入與生成草稿；後段獨立的 Executing Agent 在高權限區驗證產出並執行簽章發布，兩者之間僅傳遞經過 Schema 檢驗的 JSON 數據。
