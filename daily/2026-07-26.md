## 🔴 官方變動（事實）

- **Claude Code 預設模型升級為 Opus 5 (`claude-opus-5`)**
  - **代表意義**：提供 1M Context Window 並支援 Fast Mode ($10/$50 per Mtok)。雖然長脈絡容納量大幅提升，但 CLI 自動化大量塞入上下文時，Token 成本與「注意力稀釋」風險同步增加，需靠 Harness 端進行精確裁切。
- **導入沙盒網路嚴格白名單 (`sandbox.network.strictAllowlist`)**
  - **代表意義**：可以在配置文件中設定 Allowlist，沙盒內執行的指令若企圖連線至非白名單 Host，系統直接阻斷且不彈出提示。這大幅降低 CLI 批次外包任務時，第三方套件偷撈資料外洩的風險。
- **`/code-review` 改為背景 Subagent 執行 (v2.1.218)**
  - **代表意義**：稽核工作不再佔用主對話 Context Window，大幅減緩 Context 污染，確保 Stacked Slash Commands 運作時目標清晰。
- **動態目錄與 Subagent 串流鉤子 (`DirectoryAdded` Hook & Stream-JSON Forwarding)**
  - **代表意義**：支援跨目錄動態掛載與多層 Subagent 的 JSON 串流監控，為多 Agent 嵌套自動化（如本地 CLI 管道）提供原生觀測能力。

## 🌊 社群風向（訊號，非事實）

1. **行為約束型 (Anti-Pattern) Guardrail Skills 成為主流**
   - Repo `0xwilliamortiz/andrej-karpathy-skills` (170 stars) 與 HN 熱帖《Rules that stop AI coding agents from breaking working code》顯示：開發者不再給予 Agent 無限自由度，而是整理 Karpathy 式的盲點負面清單，透過固定規範防止 Agent 亂改無關程式碼或假造測試。
2. **Context 工程學關注點從「容量」轉向「衰退防禦與殘差壓縮」**
   - HN 熱門文章《The new rules of context engineering for Claude 5 generation models》(251 pts) 與 ArXiv 最新論文相互印證：儘管上下文升至 1M，但對話拉長後 Skill 指令會產生「注意力衰退 (Skill degradation)」。社群開始研究跨 Agent 的「殘差 context 壓縮 (Context Residual Compression)」與上下文門控。
3. **流水線化 (Pipeline-as-Factory) 解構單體 Agent**
   - Repo `finna/Finn-loop` (207 stars) 與 `skinnerlee1225/enterprise-prd-toolkit` 顯示：社群正將軟體開發拆解為「Spec 規格發想 → Build 實作 → Review 稽核」的三階獨立 Skill 迴圈，最終僅由人類進行 Merge。這驗證了「將厚重工作外包給獨立 CLI、人類專注規格與稽核」的極致自動化架構。
4. **跨 Harness/CLI 的無狀態狀態轉移 (Session Handoff) 需求湧現**
   - Repo `ImL1s/resume-skills` 與 `ToolMonsters/handoff-skill` 嘗試將 Session 導出為純文字規格，實現 Claude Code / Codex / Antigravity 間的脈絡轉移。這代表多工具交替使用的開發者需要統一的無狀態中繼格式。

## 🛡️ 安全情報

- **本日最新學界防禦事證 (ArXiv)**
  - **`ChainWatch` (ArXiv:2607.19432)**：指出基於 MCP (Model Context Protocol) 的 AI Agent 容易遭受「多步連鎖攻擊」。攻擊者將個別看似無害的 Tool Call 組合為惡意序列，單次 Call-level 的防火牆無法攔截。
  - **`ChannelGuard` (ArXiv:2607.19430)**：證實「單一安全的 LLM 模型無法直接組合成安全的 Multi-Agent 系統」。Agent 之間的通訊頻道 (Hop) 是防禦盲區，間接 Prompt Injection 很容易在 Planner 與 Worker 之間被暗度陳倉。
- **預設風險底線（Snyk ToxicSkills 基準）**
  - Snyk ToxicSkills 2026-02 對 3,984 個公開 Skill 進行掃描：**36.82% 包含安全缺陷、13.4% 為 Critical 等級、76 個已被確認含惡意 Payload**。安裝任何第三方 Skill 均同等於允許未知外國程式碼在本地執行，必須保持零信任。

2. **抽取防護型規則至自建全域 System Rules (如 `agy` / `ccr` / `Claude Code`)**
   - **驗證步驟**：
     1. 下載 `0xwilliamortiz/andrej-karpathy-skills` (T3) 原始檔。
     2. 檢查其 `.md` 內容，確認無惡意 Prompt 或外聯網址。
     3. 僅複製其「反模式負面條款」（如禁止動非相關檔案、禁止偽造 API 回應），貼入本地控制層 Prompt，強化 CLI 稽核能力。

### 中期（一個月內）
1. **針對 Substack 與知識庫自動化 Pipeline 導入「Spec-Build-Audit」三階獨立 Agent 迴圈**
   - 參考 `Finn-loop` 架構，將 Substack 發文與知識庫整理腳本拆分為三個無狀態或隔離 Context 的 CLI 步驟。避免單一 Agent 在長 Context 下產生注意力衰退，確保稽核 Agent 獨立運作。
2. **建構統一的輕量 Session Handoff 規範**
   - 制定專屬 Markdown 結案/交接模板。當 CLI 任務完成或被強制在中斷時，自動生成高密度的 Summary 檔，供下一階段的 `agy` 或 `ccr` 直接讀取，淘汰整包 Context 重讀的浪費行為。

### 長期（一季內）
1. **建立 Multi-Agent 管道之間的零信任 Schema 檢驗層**
   - 鑑於 `ChannelGuard` 論文揭露 Agent 之間通訊頻道易受 Prompt Injection 穿透，信哥自建的 IC 知識庫、BTC 監控與社群自動發文管道中，Agent 與 Agent 之間的資料傳遞必須強制經過嚴格的 JSON Schema 驗證與敏感字元過濾，絕不允許直接將上一階段 Agent 的 Raw Output 當作下階段的系統指令。
