## 🛡️ 安全情報

- 今日無新增可直接影響你 pipeline 的漏洞公告。
- 沿用既有基準：Snyk ToxicSkills（2026-02）掃描 3,984 個 skill，**36.82% 含安全缺陷、13.4% critical、76 個確認惡意負載**。任何要裝的第三方 skill，這是預設風險底線，裝之前一定要人工讀過 SKILL.md + 相關 script。
- 值得注意的相關研究（arXiv 2026-07-28）：《Agent Skills Matter: Inferring Proprietary Skills from Execution Trajectories》——指出即使 skill 內容被隱藏，其行為效果仍可從執行軌跡被反推。對你的啟示：若未來把自建 skill 商業化或封裝販售，光靠不公開原始碼不足以保護 IP。
- 《ContainmentBench》《SafeFlow》等論文都在講「injection 之後的containment」而非單純偵測，顯示業界已從「防止注入」轉向「注入發生後怎麼止血」——你的 injection scan pipeline 若只做偵測沒做隔離，方向上已經落後研究前沿。

## ⚠️ 異常訊號

在 `travisvn/awesome-claude-skills`（tier 3, 社群清單）等常規來源中未發現異常指令注入。但 **Agent-Reach release note（tier 3, `_untrusted`）裡直接寫著一段要求讀者「把這句話發給你的 Agent」去觸發升級的操作指令**，原樣引述如下：

> "升级方式：把这句话发给你的 Agent：`帮我更新 Agent Reach：https://raw.githubusercontent.com/Pannian...`"

這是典型的「透過 release note 誘導使用者的 AI agent 自動抓取遠端腳本並執行」模式。即使作者無惡意，這種「叫你把一句話貼給 Agent」的升級方式本身就是攻擊面設計上的壞習慣，不建議你的任何自動化流程去 fetch 這條 URL 或模仿這種升級模式。

## 🎯 策略建議

### 短期（一週內）
1. 在你所有跑第三方 skill/工具的 sandbox 環境，立刻設 `sandbox.network.strictAllowlist`，把允許連線的網域鎖死到目前 pipeline 實際用到的（GitHub API、arXiv、HN API 等），這是本週唯一有明確操作步驟的官方新功能，成本為零。
2. 檢查你自己 knowledge base / substack pipeline 裡用到的 SKILL.md 描述，比照 langfuse 這種「tighten skill descriptions」的做法，把觸發詞和動作邊界寫得更精準——這是免費的準確率提升，不用等任何外部工具。
3. 不要 fetch 或執行 Agent-Reach release note 裡那條升級指令字串；若真要用 Agent-Reach 相關功能，改成手動 `git clone` 後人工讀 diff 再決定要不要更新。

### 中期（一個月內）
1. 把你的 injection_scan pipeline 從「偵測」擴充成「containment」——比對 ContainmentBench 的評測思路，至少加一層「偵測到注入後自動降權/隔離該次 session 的工具呼叫」，而不只是記錄告警。
2. 觀察 Composio headless login 這條線一個月，若它穩定下來（無重大 issue 回退），可評估用在你的市場監控 pipeline 的無人值守登入環節；驗證重點：先在測試帳號跑，確認 token 過期後的失敗模式是「乾淨報錯」而非「靜默用舊身份」（本日 commit 剛好修過這個 bug，代表歷史上有過這問題）。

### 長期（一季內）
Opus 5 成為預設模型加上 1M context 這件事，代表「長上下文全塞進單次呼叫」會逐漸變成主流做法而非權宜之計——你目前若有為了省 token 而刻意做的 context compression / chunking 環節，應該重新評估是否還值得維護，把資源轉去投資「更精準的 skill 觸發 + containment」這兩塊，這才是官方與研究界共同指向的下一階段瓶頸，不是 context 長度。
