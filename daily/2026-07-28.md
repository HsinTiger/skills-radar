## 🌊 社群風向（訊號，非事實）

- **跨 CLI Agent 的記憶體外置化（MemU）**  
  **判讀**：社群正嘗試將上下文記憶（Memory）從特定的 CLI（如 Claude Code 或 Codex）中解耦。這印證了「記憶層必須是獨立 DB」的趨勢。針對你的 Substack 與 IC/WiFi 知識庫 pipeline，記憶體不該綁死在特定 CLI 的工作區內，而應外置成獨立數據庫供多個工具共同讀寫。
- **Agent Skill 邁向工程化與語言伺服器化（Skill-language-server, Dr Skill）**  
  **判讀**：Skill 已不再只是隨手寫寫的 Prompt，社群開始為其開發 LSP（Language Server Protocol）與 Loadout 管理器。隨著 pipeline 中的 Skill 複雜度大幅提升，靜態型態檢查、語法診斷與 Context 佔用率剖析（Context Profiler）將成為標配。
- **學界主導「情境式特權隔離」架構（Twin Agent, Protocol-Level Attacks）**  
  **判讀**：arXiv 最新論文（如 *Twin Agent* 與 *Agent Security Needs Redefinition*）指出，傳統僅靠「檢測指令內容是否惡意」的防護手段已宣告失效。真實的威脅來自協定層與上下文邊界突破。將「未受信任的資料讀取 Agent」與「高特權的執行 Agent」物理切離，是目前唯一能防守邊界風險的架構。
- **本機 CLI 執行環境的輕量化沙盒與隔離（Claude Playbooks, VM Runners）**  
  **判讀**：直接在開發者本機 Host 執行具備完整 Shell 權限的 Agent CLI（如 Claude Code / agy）風險過高。社群正快速往「一單元一隔離 VM / 一 isolated session」靠攏，防止 CLI agent 的誤操作毀損本機環境。

## 🛡️ 安全情報
- **理論突破**：arXiv 最新論文 (*Agent Security Needs Redefinition*, 2607.22024v1) 明確指出，Agent 安全本質上是「情境（Context）問題」而非「內容（Content）問題」——例如「刪除使用者資料」在管理情境下是正常操作，在未受信任輸入引導下則是攻擊。單靠過濾關鍵字無法防止越權。
- **協定漏洞**：*Protocol-Level Attacks on Agentic Commerce* (2607.21824v1) 證實，當 Agent 處理交易或金鑰時，主要風險來自 Agent 與 API 協定間的交互漏洞，而非單純的 Prompt 偏離。
- **既有基準底線**：Snyk ToxicSkills 2026-02 掃描 3,984 個 skill，36.82% 含安全缺陷、13.4% critical、76 個確認惡意負載。**任何未經審查的第三方 Skill 預設皆視為含有危險負載。**

## 🎯 策略建議

### 短期（一週內）
1. **建立 Substack / 市場監控 Pipeline 的「讀寫特權分離」**：將網路爬蟲與外部資料抓取模組限縮在無本機檔案寫入與 Shell 執行權限的純解析環境，嚴禁將未過濾的網頁原文直接丟給帶有高執行權限的本機 CLI（Claude Code / agy）。
2. **導入 Token 佔用率診斷（Context Profiling）工具驗證**：針對既有 IC 知識庫 pipeline，檢查是否有重複載入厚重 prompt 的情況，清理不必要的 context 消耗。

### 中期（一個月內）
1. **重構知識庫記憶體（Memory）架構**：參考 MemU 設計，將 Manbao 知識庫與 IC/WiFi 知識庫的歷史對話與摘要從 CLI 本體抽離，統編為獨立的向量/關聯數據庫，實現跨 CLI 工具（agy / ccr / Claude Code）共享。
2. **實施 Skill 靜態審查機制**：在 pipeline 自動載入任何 Skill 前，強制加入靜態語法與安全性掃描（檢查是否包含未授權的 `curl`、`eval` 或動態程式碼執行指令）。

### 長期（一季內）
1. **全面轉向雙 Agent（Twin Agent）架構**：將你的自動化體系升級為「前端低特權代理（擷取與整理） + 後端高特權代理（執行與發布）」的雙層模型。中間必須設有規範化的規格檢查點（Spec Checkpoint），由你進行最終稽核。這能將出局風險（本機資料外洩或系統損毀）降至零。
