## 🎯 策略建議

### 短期（一週內）
- 在你跑無人值守 agent 的 pipeline（市場監控、社群發文）中，測試並啟用 `sandbox.network.strictAllowlist`，先在測試分支限制網域白名單，觀察是否誤擋合法 API 呼叫，再上生產。
- `/code-review` 背景 subagent 化：若你有用 `/code-review` 在稽核環節，升級後重新量測一次 context 佔用量，確認省下的 token 額度可否挪給知識庫摘要任務。
- `humanizer-stack`（T3，119★，無法驗證作者背景）：不要直接裝。驗證步驟＝clone 後手動讀完兩支 pass 的 prompt 內容，確認無外部網路呼叫、無可疑 shell 指令，再決定是否借用其兩段式邏輯自己重寫成內部 skill。

### 中期（一個月內）
- 評估 Opus 5（1M context, $10/$50 per Mtok）取代目前 baseband 與 WiFi 知識庫摘要用的模型：用你既有 timescale_summaries pipeline 跑一次 A/B（同一批 facts，Opus 5 vs 現用模型），比較摘要品質與成本比。
- 追蹤 `skill-language-server` 與 `Dr Skill` 這類「skill 治理層」工具的成熟度，一個月後若有 T2 以上（作者可查、有 CI）的版本出現，考慮導入你自己的 skill 目錄做 lint，避免自建 skill 隨時間腐化成沒人敢動的黑箱。

### 長期（一季內）
- 推論：生態正在從「Skill 數量擴張」轉向「Skill 治理 + 注入後容忍度評估」（ContainmentBench、Skillware、Dr Skill 同時出現不是巧合）。你的自動化體系應提前建立「skill 版本鎖定 + 變更 diff 稽核」流程，而不是等生態工具成熟才補救——現在就用 git submodule 或 lockfile 方式管理你引用的所有第三方 skill 版本。
- 推論：官方持續往「長 context + 嚴格沙盒」兩端發展，可能提高單一長 session 的可行性，但不足以證明官方否定多 agent 拆分。若你的 pipeline 目前採多 agent 架構，一季內可用相同任務做長 context 與多 agent A/B，以協調成本和證據完整度決定，而非預設任一架構必勝。
